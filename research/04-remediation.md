# 04 — Remediation

## 1. Authentication

Enabled the JDK's password-file authenticator:

* `jmx.remote.x.password.file` — `username password` pairs (`operator`,
  `readonly`).
* Credentials are generated randomly and never committed.

**Validation:** anonymous and invalid-credential connections are rejected with
a `SecurityException`; valid credentials succeed.

## 2. TLS

Enabled TLS on the connector with mutual authentication:

* Server identity: a certificate (CN/SAN `target`) signed by a local CA.
* Client identity: a client certificate signed by the same CA.
* `needClientAuth=true`: the server requires and verifies a client
  certificate.

**Validation:** a client trusting only the lab CA succeeds; a client with an
untrusted CA/identity fails the handshake (`PKIX path building failed`). Trust
is never disabled to make a test pass.

## 3. Authorization

Restricted access by role via `jmx.remote.x.access.file`:

* `readonly` → `readonly` (reads only).
* `operator` → `readwrite` (the controlled operation).

**Validation:** the read-only principal can read but its attempt to invoke
`enableMaintenance` is denied with `SecurityException: Access denied`.

## 4. Network restrictions

* The lab network is `internal: true`; no JMX/RMI port is published to the
  host, LAN, or Internet.
* Containers drop all Linux capabilities, run non-root, use read-only root
  filesystems, and are resource limited.

**Validation:** `ss` on the host shows no listener on 1099/9090; the network
inspection reports `Internal=true`.

## 5. Credential and key management

* Generated by a reproducible script into a gitignored directory.
* Never committed; templates only.
* Synthetic material only; no real credentials.

## 6. Certificate validation

* Client verifies the server against a CA it trusts.
* Server verifies the client certificate (mutual auth).
* The untrusted identity is issued by a separate CA to prove the validation
  is real, not cosmetic.

## 7. Operational considerations

* A plaintext registry remains on 1099 by design (see
  `docs/architecture.md`). If the registry must also be protected, bind it
  with an SSL server socket factory and configure the connector's internal
  bind accordingly; the connector channel (9090) is already TLS-protected
  here.
* Rotate generated certificates and passwords before any real use.
* Restrict the JMX password file to a non-world-readable mode in a real
  deployment (the lab relaxes this so a non-root container user can read a
  bind-mounted file).

## 8. Validation that remediation works

`evidence/hardened-verify.txt` shows all six hardened scenarios passing:
authorized access succeeds while anonymous, invalid-credential, read-only
mutation, and untrusted-TLS accesses are each rejected.
